Detailed explanations

Return here when you want the what → why → numerical meaning → key takeaway for any stage. Each section links to the next.

1. Input photographs and camera views

What do we start with?

Multiple photographs of the same stationary scene taken from different positions. Camera A, B and C capture different 2D observations. They remain fixed throughout optimization.

Why is this needed and what comes next?

Overlapping views provide geometric evidence for COLMAP and separate image inputs to the pretrained SAM encoder. COLMAP estimates 3D positions and camera poses; SAM supplies feature targets. Neither step is itself the learned 3D feature field.

What do the figures mean?

The three RGB views below are synthetically generated reference observations. In your experiment there were 103 original photographs, with 99 registered by COLMAP. The toy scene is not your actual indoor reconstruction.

Key takeaway: three cameras observe one 3D scene; their photographs are fixed supervision, not trainable variables.

2. A frozen SAM encoder produces 2D feature maps

What do we start with?

One RGB image per camera. In Feature 3DGS, pretrained SAM is used as a frozen 2D teacher; it is not newly trained on the photographs.

Why and what comes next?

The teacher supplies numerical feature targets. For your data the tensor shape was C × H × W = 256 × 48 × 64: 256 descriptor channels per location, 48 rows (Y), and 64 columns (X). Different cameras may produce different values for different visible surfaces and image context. Stage 3 builds the student representation that will learn to reproduce these targets.

What should I click?

Select Camera A or B, click a pixel in the illustrated teacher map, and examine the first three toy channel values. The 256-slot panel distinguishes the full real-model feature dimension from the three-channel classroom simulation. The false colors are not object labels or masks.

Key takeaway: SAM feature-map values are fixed 2D teacher targets, not semantic values that are pasted directly onto 3D Gaussians.

3. COLMAP geometry + Gaussian feature initialization

What do we start with?

COLMAP estimates camera intrinsics/poses and sparse 3D feature locations from overlapping photographs. A conventional 3DGS model creates Gaussian primitives seeded at those locations, with trainable geometry, opacity, and appearance attributes.

Why is this needed and what comes next?

Feature 3DGS adds a new semantic feature parameter vector per Gaussian. In the original reference implementation, the new semantic parameters are initialized to zeros. For your initial 38,558 points, a full 256-channel feature tensor would conceptually have shape (38558, 256); densification can change the row count later.

What do the figures mean?

The diagram shows synthetic sparse 3D locations and camera poses. The selected Gaussian's 256 slots are parameters associated with the same primitive, not new spatial directions, not 256 Gaussians, and not the copied feature vector of a specific pixel. This toy learns only three active channels, with all remaining slots explicitly inactive.

Key takeaway: 3D Gaussian feature vectors begin as trainable scene parameters; their link to SAM arises through rendering and gradients.
↑ Back to Stage 3Next: the 2D–3D link →

4. The numerical bridge: 3D Gaussians → 2D feature locations

What do we start with?

Camera poses, visible 3D Gaussian primitives, and their stored feature vectors. These are sufficient to render a feature prediction at any image location.

Why is this needed and what comes next?

Unlike a direct pixel-to-point copy, a 2D location can receive contributions from several overlapping Gaussians. The camera projects each primitive into a 2D footprint. Its opacity and depth ordering determine effective weight wᵢ(p) = Tᵢ(p) × αᵢ(p) for a pixel p. Stage 5 then uses these weights to construct a feature vector for comparison with the teacher.

How to read the numbers

Select Camera A or B. Click the feature image. The table lists the strongest contributors for that same image location. Effective rendering weight is not an assigned semantic importance score: it is derived from 2D footprint, opacity and visibility. A Gaussian can have different weights at different pixels and camera viewpoints without changing its stored feature parameters.

Key takeaway: projection and compositing create the geometric 2D–3D correspondence; they do not decide that one SAM feature belongs exclusively to one Gaussian.
↑ Back to Stage 4Next: feature loss →

5. Numerical feature rendering and feature loss

What do we start with?

A fixed teacher map from Camera A, current stored Gaussian feature vectors, and the camera-dependent rendering weights from Stage 4.

Why is this needed and what comes next?

The student feature prediction at image location p is conceptually F̂(p) = Σᵢ wᵢ(p) fᵢ. The page calculates this from the actual simulated weights, then shows the fixed teacher target and per-channel difference. The educational toy minimizes a three-channel mean squared error (MSE). The published method uses a feature L1 term as part of a combined RGB and feature objective.

What should I notice?

The teacher feature vector is not updated. The student's rendered feature is not a separately stored 2D variable; it is recalculated from the current Gaussian parameters. Stage 6 turns the discrepancy into gradients for the shared 3D vectors.

Key takeaway: the teacher defines what to reproduce; render weights and Gaussian feature parameters determine the student's predicted value.
↑ Back to Stage 5Next: multi-view training →

6. Gradients and multi-view training of the same Gaussians

What do we start with?

Teacher maps for A, B, C and one shared set of Gaussian feature parameters. The same Gaussian can be visible in multiple views at different 2D positions.

Why is this needed and what comes next?

When training Camera A, gradients update features in the shared 3D representation. Later Camera B starts from those already-updated values, not from zeros or a separately constructed model. Therefore B's update can change A's next feature prediction even if A was not selected for that update.

What happens mathematically?

In a one-Gaussian toy with one channel, the prediction is f̂_A = w_A f and half-squared-error loss is L_A = ½(w_A f − t_A)². The gradient with respect to the shared feature is ∂L_A/∂f = w_A(w_A f − t_A). Substitute B's camera-specific weight and target to obtain its gradient on the same f. Our full toy uses three channels, pixel-wise MSE, and Adam-like updates; its shared parameter vectors are visible in the inspector.

What about RGB + semantic joint learning?

In the actual Feature 3DGS training loop, RGB and feature losses contribute to one overall objective. RGB appearance coefficients receive direct RGB-loss gradients; semantic feature vectors receive direct feature-loss gradients. Shared geometry and opacity can receive gradients from both. Our classroom optimizer freezes geometry/RGB and updates only feature vectors so this link is easier to inspect. The gradient-routing diagram explicitly identifies what is and is not simulated.

Key takeaway: multiple images supervise the same persistent scene parameters; RGB and semantic loss branches are separate but can act on shared geometry.
↑ Back to Stage 6Next: novel-view segmentation →

7. Novel-view features and point-prompt segmentation

What do we start with?

A trained 3D feature representation; no SAM image encoder needs to process a new rendered RGB view just to obtain the student feature map.

Why is this useful?

Moving the virtual camera changes projection and visibility, not the stored Gaussians. The feature renderer produces features at the new 2D view. The paper can pass appropriate rendered features to the SAM mask decoder for point- or box-prompt segmentation. The toy instead selects similar descriptors and is not equivalent to the SAM mask decoder.

What should I observe?

Change the camera angle, prompt a region in the novel RGB image, and compare the feature view with a simple similarity-based selection. We should not assume these selections are guaranteed to identify 3D object instances consistently across all views without further validation.

Key takeaway: the learned 3D feature field is reusable across views, and a downstream model can interpret its projected features.
